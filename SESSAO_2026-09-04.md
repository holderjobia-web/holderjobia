# Sessão 2026-09-04 — holderjob

Resumo do que foi feito nesta sessão de trabalho no backend do **holderjob**
(SaaS de inteligência financeira / CFO-BI, ambiente **dev**).

---

## 1. Contexto de entrada

A sessão começou com um bug em produção-dev: o **upload de DRE** e depois o
**login** pararam de funcionar, com o navegador reportando erro de **CORS**:

```
Access to XMLHttpRequest at '.../admin/auth/login' from origin
'https://holderjobia-seven.vercel.app' has been blocked by CORS policy:
No 'Access-Control-Allow-Origin' header is present on the requested resource.
```

---

## 2. Diagnóstico (o "CORS" era um sintoma, não a causa)

Investigação por camadas, com testes diretos via `curl`:

| Teste | Resultado | Conclusão |
|-------|-----------|-----------|
| `OPTIONS /admin/auth/login` (preflight) | **200** com `access-control-allow-origin` correto | Config de CORS está OK; a origem da Vercel **está** liberada |
| `POST /admin/auth/login` | **500** "Internal Server Error", **sem** header CORS | Exceção não tratada no banco escapava do middleware CORS |
| `GET /health` | **200** `{"status":"ok","ambiente":"dev"}` | Serviço no ar |

**Causa raiz:** o backend estava recebendo `Invalid API key` do Supabase em toda
query ao banco. Como a exceção não era tratada, virava um **500 cru** que
**não passa pelo middleware CORS** (o `ServerErrorMiddleware` do Starlette é o mais
externo de todos). Resultado: o navegador via "falta header CORS", mascarando o
problema real, que era o **banco recusando a chave**.

---

## 3. Correções aplicadas no código (commitadas em `dev`)

### 3.1 CORS como middleware mais externo — `backend/main.py`
Reordenado para o `CORSMiddleware` ser adicionado **por último** (fica mais externo),
garantindo headers CORS até em respostas de erro tratadas.
Commit: `fix(api): CORS como middleware externo + trata APIError de banco como 503`

### 3.2 Tratamento de falha de banco nas dependências de auth — `backend/core/auth.py`
- `from postgrest.exceptions import APIError`
- Novo `_BANCO_INDISPONIVEL` (HTTP **503**)
- `usuario_atual` e `admin_atual` passam a capturar `APIError` → retornam **503 limpo**
  (que flui pelo CORS) em vez de 500 cru.

### 3.3 Tratamento de falha de banco nas rotas de login — `backend/routes/admin_auth.py` e `backend/routes/auth.py`
- Queries de login (`admins` e `usuarios`) envoltas em `try/except APIError` → **503**.
Commit: `fix(auth): trata APIError nas rotas de login (503 com CORS em vez de 500 cru)`

**Efeito:** falhas de banco agora aparecem como **503 "Serviço temporariamente
indisponível"** com headers CORS presentes — erro honesto, sem enganar como "CORS".
Confirmado por `curl`: o login passou a responder **503** com `access-control-allow-origin`.

---

## 4. Investigação da chave do Supabase

- A `service_role` do projeto dev (`jzmktmzqoopejitkdazp.supabase.co`) foi testada
  **direto na API REST do Supabase**:
  ```
  GET /rest/v1/admins  →  200 OK
  ```
  **A chave é válida** e a tabela é acessível.
- Confirmado no código que o cliente lê **`SUPABASE_SERVICE_KEY`**
  (`config.SUPABASE_KEY` → `supabase_client.py`), e que **não há `.env.dev` no repo**
  sobrescrevendo (só `.env.example`). Ou seja, na Railway vale a variável do painel.

**Conclusão:** a chave está certa no Supabase, mas o **container da Railway ainda
rodava com um valor antigo/diferente** — era preciso um redeploy pegando a variável nova.

> ⚠️ **Pendência de segurança:** a `service_role` foi colada no chat durante o debug.
> **Gerar uma nova** (Supabase → Settings → API → rotacionar JWT secret) e atualizar
> na Railway assim que o ambiente estabilizar.

## 5. Bloqueio atual (fim da sessão): builder da Railway

Ao tentar **Redeploy**, a Railway falhou porque passou a usar o **Railpack** (novo
builder padrão) em vez do **Nixpacks**:

```
Railpack could not determine how to build the app.
⚠ Script start.sh not found
```

O app fica na subpasta `backend/`, e o Railpack não detecta isso sozinho.
O `railway.toml` já pede `builder = "NIXPACKS"`, mas o **Builder configurado no painel**
do serviço está sobrepondo.

### Ação pendente (no painel da Railway)
1. Serviço backend (dev) → **Settings → Build → Builder** → trocar **Railpack** por **Nixpacks**.
2. **Deployments → Redeploy**.
3. Se não houver opção de Nixpacks, adaptar o projeto para o Railpack (config apontando raiz `backend/`).

Enquanto o deploy não sobe com Nixpacks + chave nova, o container antigo continua no ar
e o login segue **503**.
